# Clients, projects, and delivery

The portfolio displays projects as responsive cards, grouped into workspace-defined sections, retaining section, text, client and multi-tag filters. Cards show each project's icon, client, section, tags and update time. Client records also support private logos; open a client from a project card/detail link or the Clients list. Client owners and administrators can choose an icon or upload WebP/PNG/JPEG (1 MiB; square 128 × 128 recommended). Images are normalized to PNG and checked against current client access on every read. Project membership grants read access to that client's description, contacts, logo and links, including when the project uses its own contact override. Contact `position` holds the job title; the separate `role` records the relationship (for example billing approver or decision maker) and grants no application permissions.

On a project detail page, managers/team leads/admins can choose a built-in icon or upload WebP/PNG/JPEG up to 1 MiB (128 × 128 px recommended). Image reads enforce project membership; icons have their own revision, so editing artwork does not overwrite project details. [Repository links](plugins/source-control.md#project-links) connect projects directly to enabled Git providers without requiring a board.

**Projects** is an internal-member workspace at `/projects`. The directory supports text search, client, configurable section, and multiple tag filters (all selected tags must match). Each expanded section loads up to ten authorized projects at a time; **Load up to 10 more projects** fetches its next page. Collapsed sections do not fetch projects. Workspace search also includes authorized project matches.

## Project sections

Cards are grouped beneath ordered section headings, with a visible count and an empty-state message for each section. The initial sections are **Proposals**, **Active**, and **Archived**. All sections are shown by default; use the Section filter to focus on one. Counts reflect the current filters and loaded results.

Open **Administration → People & security → Project settings → Sections** to create, rename, reorder, or remove sections and choose the default for new projects. Use up to 20 sections with unique names of at most 80 characters. For example, rename the defaults and add a fourth section to use **Prototypes**, **Active development**, **Deployed**, and **Sunsetted**. Settings apply to the workspace.

Section IDs are stable: renaming or reordering does not move projects. A section containing projects cannot be removed. In Project settings, administrators choose the inactive section and grant section movement to selected internal roles or users; administrators retain this ability. Authorized viewers can drag a project card onto a section, including a collapsed section, or use its **Move project** selector. The dedicated action changes only the section and rejects stale revisions. Full project edits enforce the same movement grant. Section membership grants no additional project access. Existing `PROPOSAL`, `ACTIVE`, and `ARCHIVED` assignments are preserved on upgrade; legacy settings automatically receive the original sections. New projects use the configured default, including API creates that omit `category`.

Section headings expand/collapse their cards. A user-specific, non-secret cookie retains collapsed sections and client/section/tag filters for one year; another signed-in user gets a separate layout. The configured inactive section always starts collapsed on a new visit, even if the user expanded it previously. Project cards and other navigation cards open from their whole surface; secondary links, buttons, and move selectors retain their own actions.

## Clients, contacts, and files

A client can have many projects. Set contact details on each client in **Projects → Clients**. In **Edit project → Contacts & links**, choose **Use client contacts** to follow the linked client’s current list, or **Override for this project** to replace it with a project-specific list. An override may be empty. **Copy client contacts to project** makes an independent editable copy; subsequent client changes do not affect it. Projects without a client use only their own contacts. There is no app-wide default contact list. The app name may still identify an unlinked project.

Existing nonempty project contact lists become project overrides; existing empty lists inherit the linked client. Previously saved app-wide contacts are ignored, without altering existing client/project data. Contact edits retain the existing client-owner/admin and project-leadership permissions. Members see the effective list with its source. Projects also retain members, web links, and S3/Blob file or directory references.

Client owners and administrators edit inherited details; authorized project members can read them. Storage references never grant file access: each viewer still needs connection, root, and path permission. Hidden references are omitted from views and preserved during edits by members who cannot see them. PDF links open the existing viewer, subject to policy. Other files open their containing folder.

## Roles and team boundaries

Global roles are Super admin, Admin, Business Manager, Member, and External. **Business Manager** is a non-admin role that can create clients, projects and private boards. It follows member plugin/table policies, receives no admin-console access and gains no automatic access to unrelated projects or clients. Super admins can assign it from the Users roster; administrators can select it when creating a new account. Until configured separately, its feature limits inherit any existing Member role limits. Projects add scoped **Member**, **Team lead**, and **Manager** assignments. Project leads have Team lead authority. Only project managers, team leads, and authorized administrators edit projects, manage membership, configure project schedules, or send team reports/digests. Moving sections additionally follows the workspace movement grants described above, including a dedicated limited action for authorized members. External accounts cannot use projects.

Only administrators, Business Managers, or members with an existing project manager/team-lead assignment may create projects and clients. Authority can come from project lead, a direct leadership membership, or a leadership team explicitly linked to a project. Department membership alone does not qualify. Ordinary members cannot obtain creation authority by submitting themselves as lead/manager in a new record. Existing ownership/edit permissions remain.

Creating a project-linked board requires leadership in that specific project, including for a Business Manager. Creating a private board uses the creation roles above. Plugin activation, table write permissions and feature controls remain additional requirements. Removing leadership removes creation authority, unless another current assignment still qualifies. Create buttons follow server capability responses.

Admins create described groups with Team or Department kind, a project role, members, and tags. Explicitly linking a **Team** to a project grants its members that project role. Department membership and tags classify work without granting access. A member can belong to one department and a separate project team without seeing other teams' work.

Boards can restrict visibility to selected teams linked to their project. Project leads, project managers, and administrators retain oversight. A team lead from another team does not bypass this restriction. The same rules apply to APIs, board search, calendar deadlines, reports, and digests. Feature and plugin/table permissions still apply. Creator IDs are provenance, not permanent project access.

## Boards and tickets

Enable **Kanban boards** under Plugins. Open boards from the card directory or a project's **Open project boards** link. Managers configure columns, workflow graphs, permissions and project/team access separately from everyday tickets. Drag tickets between permitted columns, or open a ticket and choose its column. Backlog plans future sprints; managers edit sprint names/dates, start and complete sprints with unfinished work carried forward. Visible sprint ranges also appear in Calendar. Changes save immediately; optimistic revisions reject stale saves. See [Kanban 1.6.0](plugins/kanban.md).

Ticket cards, backlog rows, list rows and ticket headers explicitly label the **Owner** (the ticket assignee) and **Reviewers**, including unassigned/none states. The header stays visible on the Discussion tab. Report exports include the same role labels, with bounded excerpts and reviewer counts when there are multiple reviewers. A saved person no longer present in the accessible member list appears as **Unavailable member**.

Tickets support stable references, types/priorities, descriptions, assignees, reviewers, dates, sprints, points, blocked flags, tags, epics and subtasks. Columns supply reporting status and independent entry/exit permissions. Completing fills an omitted completion date; reopening clears it. Assignees/reviewers and selected transition members must have internal board access. Project Overview charts current tickets by actual column/stage, assignee, epic and tag across only visible boards.

Saved tickets support related/blocking links, threaded discussions and typed `@name` mentions. Recipients are checked against board access; after commit, mention and reply notifications use each member's preferences and include the comment content and a reply link. Private messages never fall back to shared chat channels. Unavailable delivery does not remove the comment. Removing a ticket removes its comments and development links. Projects can also enable the [Jira metrics, Figma design and Mermaid diagram extensions](plugins/project-integrations.md).

Enabled GitHub, GitLab, or Gitea plugins provide repository and PR/MR links for boards and tickets. Approved repositories, provider permissions, and board access are checked independently. See [source-control setup](plugins/source-control.md).

Project Overview puts direct Kanban/Jira board links and repository shortcuts next to the delivery summary. **Development settings** controls repository, branch, request and deployment tracking per project, including its boards. Link existing development resources from an approved project repository; board/ticket links return to their exact source. GitHub/GitLab deployment statuses refresh from the provider, while Gitea runs support explicit manual status tracking. These links do not create or deploy code. See [project development settings and APIs](plugins/source-control.md#project-links).

### Delivery indicators

**Delivery risk** is restricted to project managers, team leads, and administrators. Its transparent 0–100 indicator covers assignees on boards visible to the caller: 20 per overdue ticket, 15 per blocked ticket, 10 per unstarted ticket due in the next three days, and 5 per in-progress ticket above five. Completed tickets are excluded. Dates use UTC. This describes current delivery conditions, not employee performance. Scores are excluded from reports, digests, and AI inputs.

## Reports and PDF attachments

**Reports** generates sprint, monthly, or custom-period PDFs for the open project only (up to 366 days and 1,500 tickets). The board selector includes accessible boards in that project; choose one to narrow scope. Board and sprint selections from another project are rejected. Report history, downloads, cover designs and scheduled project reports stay scoped to that project. An unnumbered cover and index precede numbered page 1 (Kanban summary), page 2 (additional insights), page 3 (Sprint monitor), page 4 (average ticket lead time and creation-to-completion), then the ticket export. Fixed-width columns, repeating table headers, bounded cell excerpts and eight-line limits keep long titles/descriptions readable. Reports describe the current task snapshot matched by dates/open work; they are not a historical event ledger.

The index table labels its columns **Content** and **Page**. Project leaders and administrators can open **Design report cover**, edit up to 30,000 characters of HTML/CSS, download the raw HTML template, import an edited UTF-8 `.html`/`.htm` file, download a WeasyPrint preview and save a revision-checked design for future reports. Imports remain drafts until saved. Visible-text tokens are `{{siteName}}`, `{{companyName}}`, `{{organization}}`, `{{title}}`, `{{project}}`, `{{period}}`, `{{ticketCount}}`, and `{{generatedAt}}`. Site name uses the Application name; Company name is configured separately under Administration → Branding → Business identity. Use `<img src="{{siteLogo}}">` for the configured site logo; without one, it renders transparently. Branding values are resolved fresh when generating a report.

Upload PNG/JPEG/WebP images with filenames matching `<img src="images/banner.png">` or CSS `background-image: url("banner.png")`. Matching ignores case and relative folders. Up to eight images can total 1 MiB; inputs are decoded, stripped of metadata and reduced to 1,200 pixels on their longest side. Images remain PNG when small enough, with a JPEG fallback over the per-image renderer limit. Missing, duplicate and unsafe references are rejected. The editor lists missing filenames and allows each saved image to be downloaded, replaced or removed. Uploading the same filename replaces its draft image. HTML and images are saved together with an optimistic revision in `workspace_project_report_designs` (`assets_json` holds embedded resources). API saves/preview accept an `assets` map from filename to raster data URL; omitting it preserves existing assets, and `{}` removes them.

The server renders and validates the actual single-page A4 cover before saving it. Cover styles stay isolated from index/body styles. Scripts, forms, external/file resources and arbitrary attribute tokens are rejected; the siteLogo image token is the explicit exception. Image URLs resolve only to managed embedded resources, including CSS images. Nothing is fetched from a public URL or the renderer filesystem. Rebuild the backend, frontend and WeasyPrint worker together to activate these changes.

Lead time measures ticket start date through completion in calendar days; same-day completion is zero. A column tagged **Work started** stamps an empty start date with the UTC date when a ticket enters it, while retaining an existing date. Ordinary edits and Review/Testing columns do not invent start dates. Completed tickets without start/completion dates are excluded and their coverage is shown. **From creation to completion** appears separately beneath lead time, measuring the immutable server creation date in UTC through completion, with its own sample size and missing/inconsistent-date counts. Missing historical creation dates are never invented. Jira metrics use the same summary cards, stage donut, legend and breakdown styling as Kanban.

The lead-time average, median, extremes and distribution use exactly the same eligible completed-ticket cohort. Distribution counts must match the measured sample count. The export's Dates field shows creation, start, due and completion dates; start-to-completion length; creation-to-completion length; sprint start; and sprint duration/live age. Missing or inconsistent dates produce `N/A`, without substituting dates from another metric.

**Sprint monitor** measures completed ticket duration from its assigned sprint's start date through completion, and open/live age from sprint start through the UTC generation date. It shows completed/open averages with sample sizes, oldest open age, completion percentage, tickets completed after the planned sprint end, the six largest sprint groups, and six longest measured tickets. All scoped tickets retain their own dates/durations in the export. Missing sprint definitions/completion dates, completions before sprint start, future open sprints and unassigned tickets have explicit coverage counts. Current sprint assignment and edited sprint dates apply; past membership and historical scope changes cannot be reconstructed from this snapshot.

PDFs are saved in PostgreSQL with their source board IDs. Listing/downloading rechecks current project and board access, including team revocation. Admin PDF download policy applies: watermark mode personalizes each copy; disabled downloads also block attachments.

Authorized leaders can email the PDF **as an attachment**. The project lead is always included, plus selected active internal project members. All recipients must read every included board; choose a narrower board when team access differs. External report recipients are rejected. Email and the notification must be configured. Provider acceptance is not a delivery receipt. Reports exclude private calendars and risk scores.

## Work digests

**My work digest** previews/emails in-progress assignments, due/overdue work, and the recipient's own local/synced calendar commitments. Project leaders can send each selected internal member a personalized project digest. Leaders receive statuses, not other members' calendar contents. Missing calendar permission/plugin omits that section. Each recipient's board access is checked separately.

A configured LLM can summarize bounded facts. Summaries are labeled and ordinary work details remain. No AI, absent credentials, or provider failures leave the normal digest usable. Enabling AI sends those work/calendar facts to the selected provider. Risk indicators are never supplied.

## Manual until scheduled

Nothing is scheduled automatically. Personal schedules send the owner's digest; project schedules require leadership and internal recipients. Emailed reports always include the lead.

Schedules support daily/weekly/monthly cadence, local time, timezone, weekday, and month day 1–28. Profile, schedule, digest, and indexing forms share a grouped timezone dropdown with familiar names (such as South Africa Time and Eastern Time), city, and current UTC offset. **Find a timezone** filters by name, city, or identifier. Values remain IANA identifiers and schedules adjust for daylight saving. Defaults are **disabled**, monthly, 08:00 UTC. Monthly reports cover the previous calendar month; period reports cover seven previous days; sprint jobs select the latest newly completed sprint. Digests cover the scheduled date through seven days ahead.

The backend checks each minute, claims due rows in PostgreSQL, advances deadlines, and uses delivery deduplication keys. After downtime, work runs once rather than once per missed interval. The backend must be running. Unavailable providers are recorded for manual review, without indefinite automatic retries.

## APIs and extensions

See [API reference](api.md#projects-and-delivery) for clients, projects, members, work, sprints, indicators, reports, digests, and schedules. Existing project/group/schedule edits require revisions.

`GET /api/projects/page` accepts `category`, `query`, `clientId`, `tags`, `offset` and `limit` (1-10), applying visibility and filters before pagination. `POST /api/projects/{id}/section` accepts `{sectionId, revision}`. Cover design uses `GET/PUT /api/projects/{id}/reports/design` and `POST /api/projects/{id}/reports/design/preview`.

Plugins declare `contextTargets: ["PROJECT", "CLIENT"]` to appear in authorized contexts. Reviewed modules can add computed panels with `WorkspaceContextProvider`; ZIP pages receive context through the SDK. This never grants project or storage access. See [context extensions](plugins/project-contexts.md).
