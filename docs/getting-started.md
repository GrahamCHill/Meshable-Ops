# Development setup

Install Python 3, Docker Engine, and Docker Compose 2.24.4 or later. Run commands from the repository root.

## First startup

Generate a new private `.env` and choose an initial application admin password:

```bash
python deploy/github/setup-instance.py --local --admin-email owner@example.com
```

Use `py -3` instead of `python` when that is your Windows launcher. The helper privately prompts for a password and generates distinct runtime secrets. It refuses to overwrite an existing `.env`. Retain existing keys and database passwords when upgrading; see [initialization and security](initialization-and-security.md).

Start the MinIO development stack:

```bash
docker compose -f docker-compose.yml -f docker-compose.dev.yml up --build -d --remove-orphans
```

Or use Azure Blob-compatible Azurite:

```bash
docker compose -f docker-compose.yml -f docker-compose.dev.azurite.yml up --build -d --remove-orphans
```

Use one development override at a time. Both configure a local storage connection, not sample business records. Persisted connection settings win unless `APP_SEED_STORAGE_FORCE=true` is intentionally set for that startup. The local bucket/container name is `starter-dev`; override `MINIO_BUCKET` or `AZURITE_CONTAINER` if needed.

Open [localhost:3000](http://localhost:3000) and sign in with the admin email/password you chose. No default user, demo folder, or dashboard is inserted. Create users and shared dashboards from Administration.

## Local storage services

| Service | Host access | Backend endpoint | Credentials |
| --- | --- | --- | --- |
| MinIO S3 | `http://localhost:9000` | `http://minio:9000` | `MINIO_ROOT_USER` / generated `MINIO_ROOT_PASSWORD` in private `.env` |
| MinIO console | `http://localhost:9001` | — | Same MinIO credentials |
| Azurite Blob | `http://localhost:10000/weaveopsdev` | `http://azurite:10000/weaveopsdev` | Account `weaveopsdev`, generated `AZURITE_ACCOUNT_KEY` |

Azurite Queue/Table ports are `10001`/`10002`. Emulator ports bind to loopback. Their credentials are for local development; do not reuse them for cloud services. The wrapping key generated by the helper protects storage credentials saved into PostgreSQL.

## Operations

Use the same override as startup:

```bash
docker compose -f docker-compose.yml -f docker-compose.dev.yml ps
docker compose -f docker-compose.yml -f docker-compose.dev.yml logs -f backend frontend
docker compose -f docker-compose.yml -f docker-compose.dev.yml down
```

`down` leaves data volumes intact. Do not add `-v` to apply updates. Rebuild with the same startup command after changes.

Containers and named volumes are scoped to the Compose project. To keep an older installation intact, choose a new `COMPOSE_PROJECT_NAME` in the private `.env` or pass `--project-name weaveops` on every Compose command. A different project creates separate volumes; do not change project names when upgrading existing data. Concurrent instances also need distinct published ports. New code does not remove older containers that used fixed names.
